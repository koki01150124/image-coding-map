# order_005：技術・改良パターン表の設計と実装

## 目的

`image-coding-map`に，`optimizer_map`の「パターン表」に相当する機能を追加する．

既存の論文・手法データを分析して分類体系を設計し，その分類に基づくパターン表を実装する．

参考リポジトリ：
https://github.com/yryo1005/optimizer_map

## 1．分類体系の設計

パターン表は次の2種類を切り替えられる構成とする．

- **改良パターン表**：行＝技術的な改良パターン，列＝研究分野
- **採用技術表**：行＝採用技術，列＝研究分野

具体的な行・列の分類は事前に固定せず，既存の論文・手法データを分析して決定すること．

### 分類の要件

1. 既存ノードの技術的特徴，主要な貢献，研究分野を確認する．
2. 列は既存の研究分野を原則として使用する．変更する場合は理由を示す．
3. 行は学術的に意味があり，各パターンの違いを説明できる粒度にする．
4. 分類の重複・欠落・極端な偏りを確認する．
5. 採用技術と先行方式に対する改良内容を混同しない．
6. 今後の論文追加にも対応できる拡張性を確保する．

分類案を複数検討し，採用案と判断理由を`docs/pattern_taxonomy.md`に記録すること．

分類設計の完了後は，ユーザーの追加承認を待たずに実装まで進めること．

## 2．データ構造

論文ノードJSONを必要最小限の変更で拡張する．

採用技術と改良パターンは別々に管理すること．

パターン定義は共通ファイルで管理し，各分類にID，表示名，定義，判断基準を設定する．

既存ノードに対して，確認できた情報だけを付与する．

- 原論文・要旨・検証済みの既存情報を根拠とする
- 改良パターンは，論文の技術的貢献または確認済みの改良関係から判断する
- 根拠不足による未判定と，確認済みの非該当を区別する
- 論文以外のノードについても，適用可能性を検討する
- パターン付与の根拠を追跡できるようにする

## 3．パターン表の実装

既存サイトに「パターン表」を追加する．

### 表示要件

- 「改良パターン」「採用技術」を切り替えられる
- 行にパターン，列に研究分野を配置する
- セルに該当する論文・手法数を表示する
- 件数に応じてセルを色分けする
- 行・列の合計を表示する
- セルクリックで該当論文一覧を表示する
- 該当論文を研究マップ上で強調表示できる
- 既存の年代・分野フィルタと連携する
- ライト・ダークモードに対応する
- PCとスマートフォンで閲覧できる

複数分野に属する論文は，各分野に計上する．重複集計が発生することを明示すること．

初期状態では論文ノードを集計対象とし，標準規格・構成例・未公開研究などの扱いは明示的に区別すること．

### 空欄の扱い

- 0件：確認済みデータに該当例がない
- 未判定：根拠不足で判定できない

0件を「その研究が存在しない」と解釈させない表示とすること．

研究候補を自動提案する「＋」機能は今回実装しない．

## 4．既存機能との統合

既存の研究マップ，論文検索，比較表，詳細パネル，系譜経路表示を維持する．

パターン表から研究マップへ移動した際は，選択したパターンと分野に該当するノードを強調する．

ノード詳細パネルにも，その論文に付与された採用技術と改良パターンを表示する．

参考リポジトリの実装を調査し，本プロジェクトに適したUI構造を採用すること．ただし，ライセンス条件が確認できないコードを複製しないこと．

## 5．検証

既存テストに加えて，以下を確認する．

1. パターン定義とノードの参照が整合している
2. 未定義・重複パターンIDを検出できる
3. 未判定と非該当を区別できる
4. セルの集計値が元データと一致する
5. 複数分野への所属を正しく集計する
6. セル選択と論文一覧・マップ強調が連動する
7. 年代・分野フィルタを適用できる
8. ライト・ダークモードで表示が破綻しない
9. 既存機能が正常に動作する
10. GitHub Pagesの`/image-coding-map/`で動作する

ブラウザによる表示テストも実施すること．

## 制約

- 既存の機能とデザインを原則として維持する
- 論文の大規模追加は行わない
- 根拠のない分類やパターン付与を行わない
- パターン数を増やすこと自体を目的にしない
- 外部APIによる自動論文収集は実装しない
- GitHubへのcommit・pushは自動実行しない
- GitHub Pagesへのデプロイは行わない
- プロジェクトの既存規約に従うこと

分類案の作成で作業を停止せず，設計・実装・テスト・報告まで一連の作業として完了すること．

## AIエディタによる解釈（作業開始時に追記）

- **タスクの種類**：分類体系の設計（文書），データの拡張，Webサイトの機能追加，テスト，文書の作成である．`documentation.md` と既存の規約を適用する．
- **参考リポジトリ**：optimizer_map のパターン表は，改良パターンを派生エッジ（改良元 → 手法）に付け，「パターン × 分野／年代」の表で集計し，セルから手法を強調する構成である．ライセンスが無いためコードは複製せず，この UI の構造（表の軸，セルの件数と色，セルから一覧・マップ強調）のみを参考にする．「＋」（研究候補の提案）は実装しない．
- **列**：既存の7分野をそのまま用いる．
- **改良パターンと採用技術の分離**：改良パターンは「先行方式に対して何を改良したか」，採用技術は「方式を構成する技術要素」とし，別のキーで管理する．改良パターンの根拠は，ノードの検証済みの主要な貢献と，確認済みの改良関係（`derived_from`）とする．
- **未判定と非該当**：各ノード・各軸に判定の状態（判定済み／部分判定／対象外／未判定）を持たせる．判定済みの軸に挙がっていないパターンと，パターン定義の非該当の条件（例: 学習を行わない方式に学習型の技術は該当しない）に一致するものを非該当とし，それ以外を未判定とする．0件は「確認済みのデータに該当例が無い」ことを意味し，研究が存在しないことを意味しない旨を表示する．
- **集計対象**：初期状態は論文（`kind: paper`）のみとし，標準規格・ソフトウェア・構成例・未公開研究は切り替えで含める．複数分野の論文は各分野に計上し，行の合計は重複を除いた件数とする．
- **実施しないこと**：論文の追加，外部 API による収集，commit・push・デプロイ．
